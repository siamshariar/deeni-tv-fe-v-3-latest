# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`README.md` has the toolchain table, commands and configuration. Expo changes between SDKs: check the versioned docs for the installed `expo` major (https://docs.expo.dev/versions/v57.0.0/) instead of relying on memory, and add packages with `npx expo install`.

## What this is

A React Native port of the Deeni.tv web app (`deeni-tv-fe`, branch `fixes_to_launch` @ `a080ec2`). One codebase builds:

- **Phone / tablet:** follows the web's **mobile** view (≤768 px layout).
- **Android TV:** follows the web's **desktop** view, scaled (`unit = window width / 1280`), with D-pad focus.

Behaviour, timings and copy are ported from the web. When the app and the web disagree, the web (`components/synced-video-player.tsx`, `lib/schedule-utils.ts`, `components/previous-videos-modal.tsx`) is the reference, unless a comment here or in the code says the difference is deliberate.

## Commands

```bash
npm install                # .npmrc has legacy-peer-deps=true (react-native-tvos prerelease tag)
npm run typecheck          # tsc --noEmit
npm test                   # jest (tests live in src/__tests__/, kept locally: git-ignored)

npm run prebuild           # phone: expo prebuild --clean (EXPO_TV unset)
npm run prebuild:tv        # TV:    EXPO_TV=1 expo prebuild --clean
```

Phone and TV need different native projects: **always run a clean prebuild when switching**. `android/` and `ios/` are generated (git-ignored). Release APKs for device testing: `cd android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a` (phone) or `EXPO_TV=1 … -PreactNativeArchitectures=armeabi-v7a` (TV box). Release builds are debug-signed until a release keystore exists.

There is no lint script; run `npm run typecheck` and `npm test` before calling a change done.

## Architecture

### The broadcast model (same as the web)

There is no backend scheduler. "What's on now" is computed from the clock: `elapsed = now − MASTER_EPOCH_START`, `cycle = elapsed % channelDuration`, then walk the channel's programmes (`src/lib/schedule/schedule.ts`). Every client lands on the same programme and second.

- `now` is the **server-corrected** clock (`src/lib/serverClock.ts`): every HTTP reply's `Date` header measures the device's offset. A TV box with a slow clock otherwise played 10–20 s behind the web. Two clocks are in play: schedule times (`now`, `serverTime`, `startTime`) are server time, while `_fetchedAt` and every `Date.now()` difference in the controller are the device's clock. Mixing them shifts playback by the device's error (the built-in schedule stored `_fetchedAt: now`, and a box 23 s fast started 23 s ahead; fixed 2026-10-21, `liveSync.test.ts`). Offsets under 2 s count as noise, so a nearly right clock never shows such bugs: test with a device that is clearly off.
- Schedule sources, in order (`src/lib/api/client.ts`, `broadcastController.loadChannel`): external API `tv-schedules/live?lid=&iq=` (JWT in header `p`, secret `EXPO_PUBLIC_NP_AS_L`, timestamp from `serverNow()`; unset = no auth and the API answers 403). Cloudflare in front of the API blocks any request without a deeni.tv `Referer` with its own HTML 403 ("Sorry, you have been blocked", found 2026-10-21; that is why browsers on the web get through and servers don't), so every API request also sends `Referer`/`Origin` from `EXPO_PUBLIC_API_REFERER` (tested in `apiClient.test.ts`). An Express "Forbidden" (`x-powered-by: Express`) means the request got past Cloudflare and the token was refused → the deployed web app's `/api/current-video` → embedded `CHANNELS` (`src/lib/schedule/channelsData.ts`, a verbatim copy of the web data; only Bangla, English and Arabic have programmes, other channels fall back by language).
- **Channel start on TV** (2026-11-04): a channel doesn't wait for its schedule when one is known. `saveLaunchSchedule` keeps every channel's programmes (`deeni-tv-programs-<channelId>`, epoch times); while they reach now, `savedScheduleOnNow` starts the channel at once, with the API still asked: another programme in its answer switches to it (`followLateApi`), the same one only takes its timing and queue. With nothing saved the wait is 1.5 s in all (API + web route; phones keep 10 s), then the built-in schedule. Before, a slow API could hold a channel's load, its sound and its picture for 10 s, and a cold start's sound too, though the page's own start was already playing. Measured with the API refusing (no valid key): channel change 3.9–5.1 s, 8.1 s the first. **Not measured with a valid key.**
- Channel ids are the API's numeric ids (`"1"`…`"9"`); `resolveLocalChannelId()` maps them to local data by `localizationId` + Quran flag.

### Player

- `src/lib/youtube/playerPage.ts` builds an inline HTML page with the YouTube IFrame API (controls off, iframe `pointer-events: none`) and a command API `window.__deeni` (load / play / pause / mute / hold / seek / stop). It posts `boot` (its script runs: commands may come), `ready`, `state`, `firstFrame`, `progress` (every 300 ms), `nearEnd`, `end`, `error`. A video asked for before the IFrame API is ready (the first start) is passed to the `YT.Player` constructor (`videoId`, `start`, `autoplay`), so YouTube fetches it while the player sets up; a stop or pause that comes before `onReady` still applies.
- **Fast reveal** (user requests 2026-11-01/03: play as fast as possible with the sound; YouTube's own play/pause icon showing is fine; no badge on the live player). YouTube draws its top bar (title, channel), bottom strip ("More videos", logo) and a centre play/pause icon for ~3 s (phone) / ~5–6 s (TV box) after every start, seek and resume, with any playerVars, muted or not, desktop user agent or not (tested). `youtubeFlags.cropChrome`: the page clips the iframe to the 16:9 picture (`#clip`) and makes it taller by max(64 px, 14 % of the height) above and below, so the bars fall outside the picture (the video is not cropped or zoomed). On TV a start cover counts from YouTube's PLAYING and the sound comes with it (`playingUnderCover`; ~1 s sooner on the box's sparse reports). Start and stall covers lift after **0.3 s** of real playback (one progress report; on the phone a start counts from its first frame and lifts once a report shows it moving, ~0.5 s sooner: a resumed Watched preload reports PLAYING ~1 s before it moves, and the TV box's first frame can still be black, so the TV counts from the first reported movement); once the picture shows, only a freeze over `STALL_COVER_AFTER_MS` (5 s TV, 2.5 s phone) brings a cover back, and none within `NO_STALL_COVER_AFTER_REVEAL_MS` (10 s / 4 s) of a cover lifting (both players; user request: no repeated loading while playing, the TV box often pauses a moment right after a start); the page stays silent while they are up (`coverHold`, separate from mute and hold; not the end cover), so sound and picture come together. The live player shows YouTube's centre icon as it is (a Deeni logo badge, then a "● LIVE" pill over it, were removed at the user's request). The Watched player shows YouTube's icon at a programme's start and after a seek too; ▶ while paused (`PausedIndicator`: the standard convention, the icon shows what a tap does, like the bar's button; ⏸ there was reported as wrong) and ⏸ for `YOUTUBE_ICON_MS` + 1 s after the viewer resumes it (`PlaybackIndicator`, `resumeFlash`, over YouTube's own ⏸); play / pause (bar button, remote, and on phones a tap on the video; the web only shows the controls) is only play / pause: no loading cover on resume, and no stall cover for `RESUME_GRACE_MS` after it (user requests 2026-11-03). Movement = forward steps up to 2.5 s between reports (or up to the page-clock time between them plus 1 s: a busy TV box sent some 2.3 s apart); a bigger step is a jump (seek, a load's start position) and restarts the count; the catch-up check runs after 0.5 s of movement. A first frame reported more than 60 s from the broadcast, or at 0, is YouTube still at 0 before its start position applies (it made a needless seek). Channel start: without `EXPO_PUBLIC_NP_AS_L` the external API is not called (it refuses every request); the web schedule route gets 800 ms (`WEB_ROUTE_START_WAIT_MS`), else the built-in schedule starts and a later route answer from the API naming another programme switches to it (the route serves the built-in schedule while its own API call fails). TV only: YouTube is laid out at 720p and scaled to the 1080p screen (`renderScale` 1.5: YouTube picks its quality from the layout size); loads and catch-up seeks aim ahead by what the last ones took to play (learned, kept in storage `deeni-tv-player-leads`, first guesses 9 s / 4 s, max 15 s): the box (CPU capped at 1.2 GHz) needs several seconds from load to playing. Measured on the phone 2026-11-04 (Realme RMX2030): cold start 7.6–8.7 s (~12 s on the first launch after an update), channel switch 2.4–3.5 s, Watched list ≤0.5 s, Watched start 1.0–1.2 s preloaded (1.9 s for a video that resumes slowly), pause / resume / seek instant, back to live 0.3 s; TV box, 2026-11-04 (see **Live player on TV**): cold start ~13.2 s to the sound (12–13.4 s to the picture; was 22–23 s; 16–25 s on the first start after an update), back from Home 4.6 s, channel change 4.5–5 s, 7.5 s on the first one after a start (was 9.8 s), next programme 0.5–1.4 s, Watched pick 1.5–1.8 s after resting on a row (was ~9 s), 4.9 s when picked within a second of opening the list, back to live 2.2–3.2 s. Key to popup on screen: Channel 0.6–0.75 s, Schedule 0.47–0.82 s, Watched list 0.77 s (a popup's first open can take ~1.2 s), Menu no heavy frame (was 0.85–1 s, 0.7–0.9 s, 0.75–1.3 s, ~1.9 s; `fr/tvframes.sh`, gfxinfo framestats). The rest is YouTube's own start on the box. Measured with temporary `[perf]` logs (since removed) and `logcat`; on the TV box requestAudioFocus comes 0.5–2 s after a cover lifts (with the unmute), and also at the start of a muted video, so check which.
- **End of a programme:** TV (user request 2026-11-04): the video stays on screen with its sound until it ends, with a small `UpNextCard` (thumbnail, "UP NEXT", title; `upNextCard` in the broadcast store) in its last 15 s, and the next programme is already loaded: the live page has a second, hidden YT.Player (`player2`, same page so they share one media session; made 40 s before the end, `createNext`; `prepareNext` loads the next programme muted 15 s before the end and holds it on its first frame), and a `load` of that video swaps the two players. So the next programme comes straight in with no loading screen, 0.5–1.4 s after the end (~9 s with a load; 15 s because at 30 s it waited ~20 s, Chromium dropped its decoder and the running video stuttered; no stutter in the samples at 15 s). If it isn't ready yet, the swap still happens under the loading screen (~2.5–4 s). Memory on the box: ~120–200 MB free with all three players. A channel change or the Watched player stops the hidden one. YouTube's own end-screen cards can show in those seconds, on videos that have them: only a full cover could hide them, which is what was asked away (it hid the last 20 s). Phones: the end cover (`youtubeFlags.coverEndScreen`, hides YouTube's end-screen cards, last 3 s) is an "UP NEXT ‹next title›" card (`BrandedCover upNext`, `endCover` in the store) while the programme's last seconds play with sound.
- **Tried, not kept: loading the channel rested on in the picker ahead** (Safe Kids' `TV_PRIME_MAIN`, 2026-11-04; muted in the hidden `player2`, OK swaps). On the TV box the hidden load takes ~11 s while the live video plays, against ~4.5 s alone. Rested 14–20 s, OK → sound was 1–2.8 s; rested 3 s 6.5 s, 8 s 4.4 s, a quick pick 6.3–7.9 s (9 s while the hidden player was first built), against 3.9–5.1 s without it. The live video stalled ~4.5 s with its sound cut while browsing, and free memory fell to ~115 MB (145–198 MB without it). Held paused more than ~15–20 s, Chrome drops the decoder: the picture froze under YouTube's spinner for 8 s+. It suits Safe Kids because nothing else plays on its home screen.
- **Offline** (`src/lib/network.ts`, expo-network; on Android "reachable" = INTERNET + VALIDATED capabilities): a loss counts after 1.5 s; `NetworkBanner` (bottom centre, over everything) shows "No internet connection" while offline and "Back online" for 3 s after. Offline, the live stall ladder and the load timeout wait (no "Failed to Load"), the Watched start watchdog doesn't give up; back online, a broadcast that hasn't moved for 3 s is loaded again (`broadcast.setOnline`), a stuck Watched video gets play(), and for 60 s a stall is nudged at once with a small seek (YouTube's own network retry lags after a reconnect: on the TV box the buffered video ran dry ~15 s later and stalled until the ladder's 6 s step). Re-checked when the app returns to the foreground. Tested on the TV box with `svc wifi disable` / `enable` from a nohup script on the box (adb is root there): banner after the loss, "Back online" ~7 s after Wi-Fi returns (reconnect + validation), the video kept playing from its buffer. Opened with no internet (a box whose Wi-Fi isn't up yet): the page keeps retrying YouTube's IFrame API script every 3 s (`loadApi`; code 0 errors make no error screen), the start cover waits under the banner, and the channel starts once the connection is back. Before 2026-11-04 the page gave up: "Failed to Load" stayed after Wi-Fi returned, and Try Again reloaded the same dead page. A page whose player never came up gets rebuilt at the load timeout's retry.
- **Popups on TV** open at once (no 200 ms fade/scale: up to 1.4 s on the box; the menu has no slide or 300 ms wait either, and is first built with the bar); phones keep the web's animation. Gradients are native on TV (`experimental_backgroundImage`, `Gradient.tsx`; same look): react-native-svg draws in software on the main thread, and a popup's card and header gradients were its biggest cost. The Schedule list builds 5 rows at open. **Remote keys:** the live screen doesn't render with each key (`FsControlsAutoHide` is its own component) and the player doesn't render with each progress report (`LiveRemainingPill`, once a second): key to the app's action went from 0.35–0.6 s to 0.02–0.1 s on the box.
- **Live player on TV** (`modules/deeni-live-player`, a local Expo module; `NativeLivePlayer.tsx`; 2026-11-04, the Safe Kids idea of a player that is up before it is needed): on the TV box React Native draws its first WebView ~8 s after launch, then YouTube needs ~5 s to start and ~7 s to play. So `LivePlayerHost.kt` creates the live WebView in the activity's `onCreate` (from `DeeniLivePlayerPackage`), while React Native loads, and loads the page the previous run cached in `filesDir`; React Native's view (`DeeniLivePlayerView`) takes the WebView over when it mounts (it sits behind everything in the window's decor view until then, attached, so it runs as a visible page). The page also starts the programme on now by itself: `saveLaunchSchedule` (`src/lib/launchSchedule.ts`, at every load, programme change and sync) writes the current and upcoming programmes back to back with epoch times, the native side puts them in place of `INITIAL_MARK`, and the page's `startInitial` passes the one covering now to the `YT.Player` constructor, aiming ahead by the learned page-start-to-PLAYING time (`launch` in `deeni-tv-player-leads`, first guess 12 s; the load lead is too short, and landing >5 s behind cost a catch-up seek of ~5 s). `load` of that same video keeps it (`initialKept`; first frame reported again). The page's messages reach React Native through a `ReactNativeWebView` JS interface, kept in order until `takeMessages`, then as events; commands are `evaluateJavascript`. A new app version's page replaces the cached one (`setPage`, by a hash of the template). The very first run has no cached page and creates the WebView when React Native asks. If YouTube's player doesn't come up (twice right after an install, 2026-11-04, cause not found: a slow connection or a busy box), the load timeout's retry builds a new page at ~20 s and it recovers by itself (sound at 26 s and 57 s then, 13.3–14.5 s in the ten starts after). Settings mirror react-native-webview's for the same page. The phone keeps `YouTubeWebView` (the native module is in its APK, unused: nothing is cached, so nothing starts). **The main thread matters on the box:** Chromium's browser side runs on the app's main thread, so what blocks it blocks YouTube's start (decoder to first picture 6.6 s vs 3.6 s; ART sampling profile with `am start --start-profiler`, one run: only 1.3 of the 6.8 s after second 8 idle). So on TV: `TvCover` (user requests 2026-11-04: plain and standard) is a thin ring over the programme's picture, darkened (`ThumbnailCover`, `coverVideoId` in the store, prefetched with `src/lib/youtube/thumbnail.ts`), with the title under the ring on black on the live player (the Watched player's controls show its title); no logo, no tuning screen before it (a second heavy draw). No black screen at launch: the schedule saved for the launch also keeps the titles (`deeni-tv-programs-<channelId>`, `savedProgramOnNow`), so the first screen knows the programme at once, and the splash stays until its picture has loaded (`hideLaunchSplash`, at most 4 s; at once with no saved channel). Channel changes have no saved programme: black with the ring until the schedule answers (under 1 s). The ring is `DeeniSpinnerView` (same module; an animated vector, `res/drawable/deeni_spinner.xml`, runs on the render thread; the SVG gradient drew in software, the Reanimated ring and sweep bar ran on the main thread every frame). The control bar is first drawn when something needs it (a key, an overlay, an error): ~1 s of SVG views once, invisible until then, so it doesn't show during the first load, unlike later loads. **The page hides YouTube's frame while covered** (`hideUntilPlaying`, TV: `#clip` opacity 0 until PLAYING, on a new load and under `coverHold`): the app's own opacity doesn't reach Chromium, so YouTube's spinner went on animating behind the covers, 25–35 redraws a second through the main thread (0 with nothing to draw). A stall while playing shows nothing of ours on TV (live and Watched): YouTube's own spinner, as on YouTube; the catch-up and recovery logic still runs (`stallCover`, `tvStall`). Catch-up tolerance on TV is 8 s (5 s on phones): every catch-up is a seek of ~4 s under the cover.
- `src/player/engine.ts` (`EngineRef`) queues commands until the page's `boot` message (or the WebView's load end); `YouTubeWebView` (or `NativeLivePlayer`) hosts it. The load end only comes once YouTube's iframe has loaded too: queued until then, the first load reached the page ~1.4 s after the player was ready on the TV box (2026-11-04).
- **Startup (Android)**: the fonts are built in (`expo-font` plugin with `android.fonts` in `app.config.ts`, found by file name; `src/lib/appFonts.ts` is empty on Android, `appFonts.ios.ts` loads them on iOS), so the root layout renders at once; `plugins/withWebViewWarmup.js` creates a hidden WebView (about:blank) in `MainApplication.onCreate`, so Chromium and its renderer start while React Native loads (destroyed after 30 s; not when the TV's live page already started). Icons are imported one by one (`lucide-react-native/icons/<name>`): the package index made Metro bundle and run all ~1,800 at start (`inlineRequires` is off in Expo's config); the bundle went from 5.7 to 4.1 MB.
- `src/player/broadcastController.ts`: the live player (port of the web's `loadChannel` / `syncWithServer` / `playNextVideo` / stall ladder). Covers: tuning (TV: straight to the branded cover) → branded "Watching" cover until real movement (0.3 s with `cropChrome`, else 5 s TV / 3 s phone); stall cover when frozen >1.2 s **or YouTube reports BUFFERING** >1.2 s; before a start or stall cover lifts, it seeks to the live position if >5 s behind (`liveAnchor`; TV aims ahead by the learned seek time), at most twice per cover (a slow box behind again after every seek kept the cover up). A stall cover lifts after 0.3 s of movement with `cropChrome` (else 3 s; web: 0.6 s). When the Watched player closes on the phone, the live stream (still playing muted underneath) comes straight back with its sound if it moved in the last second and is within 5 s of the broadcast; otherwise the stall cover goes up, silent, and a stream more than 5 s behind seeks to the broadcast position first (the cover on every close added ~1 s, 2026-11-04). A programme change is triggered by an `end` for the video on screen that has already played (page and controller both check: on the TV box the old video's late ENDED skipped the next programme), or by the broadcast's clock: programme changes keep it (product request 2026-10-18; deviation, the web starts the next programme at 0 and fell further behind with every change, ~23 s after one on the TV box). From the live anchor the controller knows when what plays ends in the broadcast; 1.5 s after that it switches even if the video is behind (slow start, stall), the next programme starts at its live position (rejoining the schedule if that one is over too), and its start cover catches up like a channel start. The schedule's seekTo resets the anchor whenever it names what plays (right after a change and at every 60 s sync; never mid-programme seeks there): a channel started from the external API takes timing only from the API, a fallback channel from any tier. Tested in `src/__tests__/liveSync.test.ts` (simulated player page). Periodic sync every 60 s; it refreshes the queue only while the schedule names what plays (`periodicQueue`): after a programme change the app runs seconds behind the schedule, and the web-ported refresh (`upcomingFromSchedule`, the web's `syncWithServer` "In sync" branch) then skipped a programme (phone re-test, 2026-10-18; the web has the same bug). Background → pause, foreground → rejoin with the 5 s tolerance.
- `src/player/previousController.ts`: the "Watched Program" player, a second persistent page. Warmed when the list opens (300 ms after it is on screen: page created, first row preloaded = played muted to its first frame and held paused, so picking it only resumes it), on TV too since 2026-11-03 (its first start took ~16 s without; earlier a second page loading next to the live one stalled the live video behind the list). TV (2026-11-04): the page itself, with no video, is created 8 s after the live picture first shows (`prepareWatchedPlayer`), so YouTube's player is ready before the list opens. **The live player pauses while the list is open** (`listOpening`, back with a seek under the cover if the list closes with no pick): the box plays one video at a time; next to the live one a programme took 7–10 s to load and the live video hiccuped ~2 s, alone it takes ~3 s. The programme kept ready follows the row the viewer rests on (`rowFocused`, 500 ms; `preload` of what is already there or on its way does nothing), the load goes before the player layer's draw in `play()`, and on close the live player goes first and the Watched page is only paused, stopped 12 s later (`LATE_STOP_MS`: stopping tears YouTube's player down on the page thread both pages share, ~2.8 s). Phone: live keeps playing muted underneath (`hold`). TV: live is paused (and held silent) while it plays, and seeks back to the broadcast position on close under the stall cover (4.9 s on the TV box; stopping it tore YouTube's player down on the page thread both pages share, which held the Watched start back ~2.6 s, and the way back was a full reload, 9–15 s); a programme that ended meanwhile is rejoined with a load, at once from the built-in schedule when that is what plays. It autoplays: unlike the web (Play after 4 s, for iOS), the start watchdog keeps the loading cover while YouTube is still starting and shows Play only after 30 s (TV) / 12 s; a late start still plays. Its stall cover also goes up on BUFFERING >1.2 s, on resume and on every seek, and lifts after 0.3 s of movement with `cropChrome` (else 5 s: YouTube's title bar / play glyph / "More videos" showed otherwise). The start cover waits 0.3 s of movement with `cropChrome` (else 3 s TV / 6 s phone). Phone: the list opens first and the page is warmed 300 ms later (doing both in one frame made the list take ~1 s). The pause / end thumbnail is prefetched when a video starts (loaded on the pause, it left the picture black for ~0.7 s on the phone). TV seek-bar focus: no box; the bar thickens and the handle grows (YouTube on TV).

### UI

- One screen: `src/app/index.tsx` (live frame + `ControlBar` + `DonateButton` + `PreviousPlayerLayer` + `OverlayHost`). Overlays are a stack in `useUiStore`; hardware Back closes the top one (`useBackHandler`).
- `useFrameLayout()` is the single source of sizes (frame, bar, buttons, logo, corner radius, fullscreen box), shared by the live and the Watched player.
- The Logo uses pre-scaled PNGs (`assets/images/logo/logo-h*.png`, Lanczos from the web's 3033×595 original) picked by pixel height; one big image squeezed by the GPU looked jagged on TV.
- Rounded borders, focus rings and the loader ring are SVG (`src/components/common/Rings.tsx`): Android's own rounded borders render jagged on TV boxes.
- Phone menu: Schedule, Watched, Channel, Refresh, About, Donate. A Privacy Policy item exists but is commented out (product owner's request) in `MenuDrawer.tsx`. On TV, Donate shows a QR panel instead of opening the browser.

### TV rules (each one cost a bug)

- **Remote keys reach JS on key-up only** (react-native-tvos sends key-down only with `ReactFeatureFlags.enableKeyDownEvents`). `useTVEventHandler` code must act on `eventKeyAction === 1`; held keys arrive as `longLeft` / `longRight` (down at hold start, up on release).
- A View whose opacity or shape toggles around a focusable control or a WebView needs `collapsable={false}`; Fabric otherwise re-creates it and D-pad focus is lost. Keep focusable controls mounted under covers instead of unmounting them.
- Every `FlatList` inside a modal goes in `ModalList` (react-native-tvos wraps lists in a focus guide that doesn't shrink).
- **TV is always fullscreen** (product decision 2026-10-17; `ALWAYS_FULLSCREEN` in `src/player/fullscreen.ts`): the live and Watched players start full-bleed and can't leave it, neither bar has a Full screen button, Back closes the Watched player directly and with nothing open leaves the app, and the Donate pill (hidden in fullscreen) is reached through the menu's QR panel. Phones are windowed with a Full screen button (locks landscape), and also follow rotation like the YouTube app (product request 2026-10-18, `onPhoneOrientation`): turning the phone sideways opens fullscreen (the Watched player's when open) without a lock, turning it upright leaves it, and leaving it by button or Back while sideways rotates back to the upright screen at once (YouTube app) and holds it with a portrait lock until the accelerometer (`expo-sensors`) sees the phone held upright for 0.4 s; then rotation is free again. "Upright" (`isHeldUpright`) is judged like Android's auto-rotate: gravity in the screen's plane within ~35° of the long axis, at any tilt up to ~70° back; a phone lying flat doesn't count (Android can't tell its orientation either). The first version required 0.7 g along the long axis, and on the phone the lock never released for a phone tilted back or on a desk, so turning it did nothing (2026-10-18). Without an accelerometer it keeps the windowed landscape view until the phone is upright. Phones only (short side < 600 dp), never tablets. The bar stays up while a channel the viewer started is loading (app open or reopen, channel switch, Refresh, back from the Watched player: `userStart` → `videoStarting` in the broadcast store, cleared when the start cover lifts) and hides 5 s after the video appears, later 3.5 s after the last key. Automatic changes (the next programme, recovery reloads, schedule rejoins) leave the bar as it is, so a hidden bar stays hidden. With the bar hidden any remote key only shows it (focus/blur TV events don't count); Back on the live screen also shows it with a "Press Back again to exit" toast, and a second Back within 2.5 s leaves the app. The Watched player keeps its controls up while loading and hides them 5 s after it starts.
- Fullscreen with hidden controls: the first key only shows them (an invisible full-screen `Focusable` holds focus).
- Endless animations (`Spin`, `Pulse`, `SweepBar` in `Motion.tsx`) run only while the app is in the foreground: Reanimated keeps driving them in the background, and the "Failed to Load" screen's held the box's main thread at ~75 % after Home. Build new looping animations from these. Reanimated 4.5.1 also re-arms its mapper run every frame for the app's lifetime; worklets 0.10.1 never paused that frame queue (it didn't register for host pause, ~10 % of a core in the background), so the app uses worklets 0.10.4, which does. After changing worklets, delete the native build folders (`android/.cxx` and `android/build`) of worklets, Reanimated and `expo/node_modules/expo-modules-core`, or the build links against the removed `libworklets.so`.
- Focus returns to the opener when an overlay closes (`ControlBar` remembers the last button; `tvFocusArea` handled the Donate pill, which TV no longer shows).

| `deeni-tv-channel` | Selected API channel id; absent = first visit (mandatory channel picker) |
| `deeni-tv-channels` | `tv-channels` API list as received |
| `deeni-tv-previous-<channelId>` | Watch history, newest first, max 30 |
| `deeni-tv-programs-<channelId>` | TV only: the channel's programmes as last played (ids, titles, epoch times) |

## Testing

- `src/__tests__/` (local only, git-ignored): `webParity.test.ts` checks the ported maths against fixtures generated by running the web's own code; `serverClock.test.ts` covers the clock correction.
- Device testing is manual (an Android 9 TV box and an Android 10 phone so far). Not covered yet: iOS (needs a Mac or EAS), the API with the JWT secret, error/offline screens, long multi-hour playback.

## Open decisions

- App id is `com.deeni.tv`; the existing store app may be `com.deeniinfotech.deenitv` (to confirm before release; a store update needs the same id and signing key).
- Release signing keystore (not in the repo). Release steps (secret, Referer, version code, all CPU types, signing, permissions) are in the README's release checklist; `app.config.ts` blocks every permission but INTERNET and keeps the version code above the Capacitor app's 2.
- YouTube / store policy review before release; YouTube-chrome workarounds are switchable in `youtubeFlags` (`src/lib/config.ts`).
